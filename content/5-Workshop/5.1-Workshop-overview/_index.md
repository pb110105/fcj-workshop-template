## Introduction

This workshop builds a pipeline for electricity data ingestion, quality validation, and analysis using the EIA Open Data API.

The local implementation has been completed using PowerShell. The next phase will port the logic to Python and deploy it on AWS using AWS SAM.

## Problem Statement

Hourly electricity data includes actual demand, forecast demand, and net generation.

Manual processing requires repeated API calls, file exports, validation, and result aggregation. Missing or duplicate records can affect analytical results.

The pipeline provides a consistent workflow:

1. Read the configuration.
2. Collect data.
3. Validate data quality.
4. Analyze validated data.
5. Export datasets and reports.

If a step fails, the pipeline stops and returns an error code.

## Data Scope

| Attribute | Value |
| --- | --- |
| Source | EIA Open Data API |
| API route | `electricity/rto/region-data/data/` |
| Initial respondent | CISO — California Independent System Operator |
| Frequency | Hourly |
| Time zone | UTC |
| Unit | Megawatthours — MWh |
| Business key | `period + respondent + type` |

Selected metrics:

| Code | Meaning |
| --- | --- |
| D | Actual electricity demand |
| DF | Day-ahead electricity demand forecast |
| NG | Net electricity generation |

The data represents electricity activity in the CISO balancing authority area in the United States. DF is supplied by EIA, not generated by a model trained by this project.

## Local Implementation

### Components

| Component | Purpose |
| --- | --- |
| `collect_data.ps1` | Call the API and save JSON/CSV data |
| `check_data.ps1` | Validate quality and completeness |
| `analyze_data.ps1` | Compare D with DF and calculate MAE and WAPE |
| `run_pipeline.ps1` | Coordinate the steps and stop on failure |
| JSON configuration | Define the respondent, metrics, period, and output filename prefix |

The `-ConfigPath` parameter selects a configuration at execution time without changing source code.

### Quality Checks

- Validate required fields.
- Validate finite numeric values.
- Check respondents, metrics, and units.
- Detect duplicate keys.
- Detect missing hour–respondent–metric combinations.
- Detect records outside the configured scope.

### Analysis

- Identify hours with high electricity demand.
- Match actual demand and forecasts by timestamp.
- Calculate errors and absolute errors.
- Summarize MAE and WAPE.
- Export a comparison CSV and a JSON report.

## Verified Results

| Period | Records | Compared hours | Quality validation |
| --- | --- | --- | --- |
| September 1–30, 2026 | 2,160 | 720 | PASS |
| September 1–7, 2026 | 504 | 168 | PASS |

Tested failure scenarios include duplicate records, missing records, an empty API key, and a nonexistent configuration file.

Successful pipeline runs finish with exit code `0`; tested failure scenarios return exit code `1`.

## Proposed AWS Design

| Component | Proposed service |
| --- | --- |
| Scheduled execution | Amazon EventBridge Scheduler |
| Collection and processing | AWS Lambda |
| Data storage | Amazon S3 |
| Table metadata | AWS Glue Data Catalog |
| Analytical queries | Amazon Athena |
| Logs and monitoring | Amazon CloudWatch |
| API key storage | AWS Systems Manager Parameter Store — SecureString |
| Permissions | AWS IAM |
| Infrastructure deployment | AWS SAM / AWS CloudFormation |

S3 data is expected to be organized into the following areas:

- `raw/`: Original data received from the API.
- `clean/`: Standardized data that passes validation.
- `quarantine/`: Rejected data requiring investigation.
- `reports/`: Quality reports and analytical outputs.

The proposed Region is Singapore (`ap-southeast-1`). An architecture diagram will be added after the design is finalized.

## Implementation Status

The local processing pipeline has been completed, and its source code is managed on GitHub.

AWS deployment, API pagination, bounded retries, scheduling, Athena queries, and monitoring have not yet been implemented.
